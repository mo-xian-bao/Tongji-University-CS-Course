## 2.2 软件过程Software Process

（重要）


**对Process的分解：Process—细分为若干→Activity—细分为若干→Action—细分为最小的→task**

task是最小单元，原子性，高内聚

粒度划分：

- Activity: 力求实现一个广泛的目标——e.g：stakeholder的沟通
- Action: 包含一组产生主要工作产品的任务——e.g：架构设计；一个action要有主要工作产品work product(e.g 架构模型)
- Task: 侧重于产生实际结果的小而明确的目标——e.g：单元测试

提问：不同activity, activity的不同action，action的不同task之间的关系?(start-start/start-finish/finish-start)

回答：实际情况下，三个关系都有可能发生

一个例子：

Activities:RG过程的一个Activity

Actions: 小的project，比如上报需求到负责人，开一次腾讯会议

Tasks：比如：制定会议室时间等

**架构的三大任务：体系架构设计，接口设计，数据与数据结构设计**

### **软件工程中的普适性活动（Umbrella Activities）**

普适性活动，也称为伞状活动，是指在软件开发过程中贯穿始终，与各个阶段相互交织的活动。它们并非独立的阶段，而是支持和管理其他软件工程活动，确保项目顺利进行的关键组成部分。

根据您提供的资料，以下是主要的普适性活动：

- **项目跟踪和控制 (Project Tracking and Control)**
  
    - **目的**：监控项目进展，确保项目按计划进行，及时发现和纠正偏差。
    - **内容**：
        - **进度管理**：跟踪项目进度，与计划进行对比，识别延误风险。
        - **成本管理**：监控项目预算，确保成本控制在合理范围内。
        - **资源管理**：合理分配和利用项目资源。
        - **度量**：对进度、缺陷、工作量等进行度量，以便进行定量化管理。例如，测量每个任务的完成度，计算总体完成度，并以此制定下一阶段目标。
    - **方法**：使用诸如甘特图、燃尽图等工具进行可视化跟踪。
- **风险管理 (Risk Management)**
  
    - **目的**：识别、评估和应对项目中的潜在风险，降低风险带来的负面影响。
    - **内容**：
        - **风险识别**：通过头脑风暴、历史项目经验、专家建议等方式识别潜在风险。
        - **风险评估**：计算风险暴露度（risk exposure），即风险发生的概率乘以风险造成的损失。
        - **风险缓解**：制定风险应对计划，包括风险避免和风险缓解措施。
        - **风险跟踪**: 持续监控风险，并根据实际情况调整应对措施。
    - **重要性**：风险管理贯穿整个软件开发生命周期。
- **质量保证 (Quality Assurance)**
  
    - **目的**：确保软件产品符合预期的质量标准，满足用户的需求。
    - **内容**：
        - **质量规划**：制定软件质量目标和标准。
        - **质量控制**：执行各种质量控制活动，如代码审查、测试、检查等。
        - **SQA (Software Quality Application)**：使用清单（checklist）确保软件质量。
        - **评审**：在工作完成后进行检查，以发现缺陷。
        - **技术审查**：对代码、需求等进行审查。
        - **度量**: 度量软件缺陷, 从而进行质量改进。
    - **关注点**：
        - **产品质量**：软件是否符合需求规格。
        - **过程质量**：开发过程是否遵循规范。
- **配置管理 (Configuration Management)**
  
    - **目的**：管理软件配置项，确保软件的各个版本和组件的一致性，以及可追溯性。
    - **内容**：
        - **版本控制**：使用版本控制工具（如 Git）管理代码变更。
        - **配置项管理**：管理软件的各种配置项，如需求文档、设计文档、代码、测试用例等。
        - **变更管理**：控制软件变更，并记录变更历史。
        - **基线管理**：建立软件的基线版本，作为后续开发的基础。
    - **重要性**：配置管理对于团队协作和软件维护至关重要。
- **技术审查 (Technical Reviews)**
  
    - **目的**：对软件工程的各种工作产品进行审查，以发现缺陷并改进质量。
    - **内容**：
        - **代码审查**：检查代码的质量、规范性和可读性。
        - **需求审查**：检查需求文档的完整性、一致性和可理解性。
        - **设计审查**：检查设计方案是否满足需求，是否合理可行。
    - **特点**：技术审查是一种特殊的质量保证活动。
- **可重用性管理 (Reusability Management)**
  
    - **目的**: 提高代码的复用性，降低开发成本和时间.
    - **内容**:
        - 代码标准化，提前考虑组件复用性。
        - 重构，使代码和类标准化。
- **工作产品准备和生产 (Work product preparation & production)**
  
    - **目的**: 为软件开发活动提供所需的文档和模型.
    - **内容**:
        - 创建工作产品，如模型、文档、日志、表格和列表。

**普适性活动的重要性**

- **贯穿始终**：这些活动贯穿整个软件开发生命周期，而不是只在特定阶段进行。
- **相互支持**：这些活动之间相互支持，共同确保软件项目的成功。
- **提高质量**：这些活动可以帮助发现缺陷，提高软件质量。
- **降低风险**：这些活动可以帮助识别和应对项目风险，降低项目失败的风险。
- **促进协作**：这些活动可以促进团队成员之间的协作和沟通。

**与其他层次的关系** * 普适性活动与软件工程的各个层次紧密相关。例如，质量保证活动贯穿于需求、设计、编码、测试等各个阶段。 * 这些活动并非独立存在，而是支持和管理软件工程的核心活动，如建模，设计，开发，部署。

总之，普适性活动是软件工程中不可或缺的组成部分，它们对于确保软件项目成功至关重要。 软件工程师需要在整个开发过程中持续关注和执行这些活动，从而提高软件质量，降低项目风险。

希望这个介绍对您有所帮助。如果您有任何其他问题，请随时提出。

## 2.3 软件工程实践

### 2.3.1 实践的精髓(Essence of practice)

4步:

- 1.理解需求Understand the problem——
    - 交流(requirement gathering)
    - 计划(planning)
    
    实质：需求调研，需求工程(requirement engineering)
    
    具体问题:
    
    1.谁是项目的**利益相关者**; 
    
    2. **不确定因素，数据、功能和特性**（特性还包括一些非功能需求，如安全性，performance，都很重要);
    
    3. 问题能否划分，需求能否分解，**减小粒度**(在UML里和Use Case,Class Diagram相关)；
    
    4.问题可以**可视化表现**吗(图)，**分析模型(analysis model)能否建立;
    
- 2.计划解决方案Plan a solution——
    - analysis
    - design modeling(Use Case, Class Diagram, Sequence Diagram, Activity Diagram, State Diagram)
    - 核心是：**Architecture Design & Component Design**
    
    概况：根据上一个阶段的结果，进行建模（数据，功能等角度），提供一种解决方案（比如：框架，接口，界面，数据库的设计）
    
    具体问题：
    
    1. 有无**相似的模式**可以复用，（设计模式，相似项目，数据，功能，非功能需求等)；
    
    2.**类似的问题有无解决方法**，有无**可复用**的解决方案元素；
    
    3. 子问题能否被定义，**子问题**的解是否显而易见的（软件架构）;
    
    4.能否以一种能够有效实施的方式来**表示解决方案**？能否创建**设计模型(design model)**？
    
- 3.实施解决方案Carry out the plan
    - code generation, implementing solution 代码生成
    
    具体问题：
    
    1.解决方案是否符合计划？ 源代码是否可以追溯到设计模型（你的**代码要对应设计架构**，比如说，哪部分代码对应了某功能的微服务）
    
    2.解决方案的每个组成部分(component)是否**正确**？ 设计和代码是否已经过**审查（review 是Umbrella Activity）**，或者更好，是否已将正确性证明应用于算法
    
- 4.检查结果精确度Examine the result for accuracy
    - testing 测试
    - quality assurance 质量保证
    
    具体问题:
    
    1.是否可以**测试**解决方案的**每个组成部分?**(单元测试,每个类都有状态图State Diagram,利用状态图进行测试)，是架构设计的重要依据) 是否实施了合理的**测试策略(testing strategy)**
    
    2.解决方案是否产生符合所需数据、功能和特征的**结果**？ 软件是否根据所有利益相关者的要求进行了**验证(**validate->也叫system testing系统测试)？

## 2.4 软件开发误区Myth


**软件开发误区 (Software Development Myths)**

软件开发过程中存在许多误解，这些误解可能来自于管理层、客户或开发人员自身。这些误区往往会导致项目延期、超出预算或交付的软件质量不佳。以下是根据你的资料总结的一些主要误区：

**1. 管理层误区 (Management Myths)**

- **误区：我们已经有标准和规程来构建软件了。**
    - **现实：** **即使存在软件工程框架，也可能会遇到很多问题**。软件开发不仅仅是遵循既定的步骤，还需要灵活应对变化，并且需要**根据项目具体情况进行调整**。
    - **解释：** 软件工程提供了指导，但不能保证项目完全顺利， **需要根据实际情况灵活应用**。
- **误区：如果项目进度落后，我们可以简单地增加人手。**
    - **现实：** **增加人手可能会使项目更落后**。新加入的成员需要时间来熟悉项目，而沟通和协调成本的增加可能会降低整体效率。
    - **解释：** 这被称为“人月神话”，**软件开发不是简单的体力劳动，增加人手可能会使沟通和协调变得更加复杂**。
- **误区：如果把软件项目外包给第三方，我们就可以放松了。**
    - **现实：** 如果组织不了解如何管理和控制外包软件项目，他们肯定会遇到麻烦。
    - **解释：** 外包需要有效的管理和控制，否则可能导致更大的问题。**外包方仍然需要参与到项目管理中**。

**2. 客户误区 (Customer Myths)**

- **误区：只要我们给出了概要的需求，就可以开始编写程序，细节以后再补充。**
    - **现实：** **模糊的需求说明书是失败的根源**。不明确的需求会导致开发过程中频繁的变更，从而增加成本和延误时间。
    - **解释：** **需求必须明确，可验证和可追踪**。 **应该通过有效的沟通和持续的迭代来明确需求**。
- **误区：软件需求会不断变化，但是变更可以很容易地被容纳。**
    - **现实：** **需求的变更会带来成本的影响**。变更的成本会随着项目进展而增加，如果在后期提出重大变更，可能会导致项目返工。
    - **解释：** 敏捷开发方法允许一定程度的变更，但 **应该在迭代周期内进行管理**。**变更应该在设计或编码前提出**。

**3. 开发人员误区 (Practitioner's Myths)**

- **误区：一旦我们写完程序并使其运行，我们的工作就完成了。**
    - **现实：** 交付运行的程序只是软件开发的一部分，还需要文档，用户手册，支持等一系列内容。
    - **解释：** 软件的生命周期包括开发、部署和维护，**维护和支持同样重要**。
- **误区：在早期就花大量时间编写精细代码，是很有必要的**。
    - **现实：** **代码需要快速迭代而不是慢而精**，应该通过有效的软件质量保证机制，例如review， 来保证代码质量。
    - **解释：** 应该采用迭代的方式进行开发，**快速构建原型，并在后续迭代中进行改进**。
- **误区：单元测试是保证软件质量的唯一手段。**
    - **现实：** 除了单元测试，还有其他多种保证软件质量的方法，如代码审查等。
    - **解释：** 应该使用多种质量保证方法，如技术审查、测试等。**技术评审是比测试更有效的质量过滤器**。
- **误区：软件工程是关于创建大量文档的，这会使我们变慢。**
    - **现实：** 软件工程的核心是创建高质量的产品，**文档是为了支持这个目标**。高质量的代码可以减少返工，从而加速开发过程。
    - **解释：** 文档是为了更好的沟通和维护，而不是为了文档而文档，好的文档可以帮助理解代码，从而加速开发过程。

**总结**

- **核心问题：** 这些误区反映了对软件开发本质的误解，例如：
  
    - 误认为软件开发是一个线性的过程，而实际上是一个迭代的过程。
    - 误认为软件开发是纯粹的技术活动，而忽略了人、沟通和管理的重要性。
    - **误认为软件开发是可预测的，但实际上充满了不确定性**。
- **解决之道：**
  
    - 理解软件工程的原则和方法。
    - 加强沟通和协作。
    - 采用迭代和敏捷的开发方法。
    - 重视质量保证活动。
    - **保持灵活性，并对变化做出快速反应**。

了解这些误区有助于我们避免在软件开发过程中犯同样的错误，从而提高软件项目的成功率。
