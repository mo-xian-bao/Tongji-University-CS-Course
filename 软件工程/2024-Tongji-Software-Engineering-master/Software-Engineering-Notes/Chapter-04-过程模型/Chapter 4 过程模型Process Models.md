## 4.1 规定的过程模型Prescriptive Process Models

"prescriptive": 规定了一系列过程元素：framework activities, SE actions ,tasks ,work product, quality assurance , change control mechanisms

### 4.1.1 瀑布模型The Waterfall Model

特点：

1. 按照general/standard process顺序开发，很少迭代：planing是umbrella可以去掉
2. 过程明确，需求清晰
3. 不主张迭代，但也有迭代
4. 用户需要很长时间才能得到成品
5. 某阶段受阻，整个项目都会到blocking states，也就是说，没有形成milestone，一个action，task卡住了就都卡了
6. 线性模型
7. 项目大的时候不要用，适合需求清晰稳定的情况

Planning: EST评估→计划→跟踪

瀑布模型的缺点：

waterfall models的问题：

①**实际项目很少遵循模型提出的顺序流程**。 虽然线性模型可以适应迭代，但它是间接这样做的。 因此，随着项目团队的推进，变更可能会导致混乱。（项目发生变更时就不适用，导致混乱）

② **客户通常很难明确地陈述所有要求**。 瀑布模型需要这一点，并且难以适应许多项目开始时存在的自然不确定性。(要求需求明确，然而这点很难做到）

③ 客户要有耐心。 **程序的工作版本要到项目时间跨度的后期才可用**。 重大失误如果在审查工作计划之前未被发现，可能是灾难性的。(比如：waterfall会导致“阻塞状态”，在这种状态下，某些项目团队成员必须等待团队其他成员完成依赖任务。)（容错率低，且在项目后期发现难以修复，and阻塞状态）

### 4.1.1(extended)V-模型

瀑布模型的变种 (与standard process非常相似）

瀑布模型对软件工程的最大贡献

描述了质量保证行动与与沟通、建模和早期建设活动相关的行动之间的关系。

Unit Testing: 因为需要看底层代码，故依赖Code generation；因为复杂的代码中如何传参，参数指向什么很复杂，需要查看Component Design 和 详细设计规约

Integration Testing：组件与组件的集成，看Component Design；还因为是和子系统之间的协作有关，涉及接口，数据库，软件结构设计，需要参考接口设计，数据设计，软件体系架构设计，故看Architectural Design

System Testing：把编好的程序放在各种集成环境下；首先需要需求分析规约来进行模拟测试（主要看的是需求建模中的功能建模），比如模拟Actor，故需要Requirement Modeling；如果发现失败了，要检查什么接口有问题，故要参考Architectural Design( 追溯子系统 )

Acceptance Testing: 验收测试是面向用户的，用户不知道你的实现细节而是以需求为依据，所以是需求层面的（需要用到需求规约和需求分析规约），即Requirement Modeling

### 4.1.2 增量过程模型

场景：

1. Non-linear开发工作的整体范围排除了一个纯粹的线性过程。
2. Rapid Raw Product v1.0 可能迫切需要向**用户快速提供**一组有限的软件功能，然后在以后的软件版本中完善和扩展该功能。
3. Update v2.0++++ 有部分功能**不成熟需要后期才增量补充**；
4. Preview Function 市场要求**先发布一部分功能**，后续功能增量补充；
5. Parallel 一些内容**交叉进行**

结合了waterfall模型和并行处理流parallel

当使用增量模型时，**第一个增量通常是核心产品**。 也就是说，**解决了基本要求**，但许多补充功能（一些已知，另一些未知）仍未交付。 核心产品由客户使用（或经过详细评估）。 作为使用和/或评估的结果，为下一个增量制定计划。

特点：

- 每一次增量都生成可发布的产品increment producut，第一个增量形成核心基本产品，后续增量形成完善版本
- 每次增量是一个waterfall，一次增量内不主张迭代
- 不同增量间可并行开发（比如：第2个做coding时，第3个可做需求建模）——纵轴重合

迭代发生在原型被调整以满足不同利益相关者的需求时，同时使您能够更好地了解需要做什么。

## 4.2专用过程模型

### **4.2.1. 基于构件的开发 (Component-Based Development, CBD)**

- **概念**：基于构件的开发是一种软件开发方法，它强调通过**组装和集成可复用的软件构件**来构建应用程序。这些构件可以是预先构建的、经过测试的、并且具有良好定义的接口的软件模块。
- **核心思想**：**重用现有的软件资产**，而不是从头开始构建每一个应用程序。
- **构件**：
    - 构件通常是**独立的、可部署的软件单元**，具有特定的功能和接口。
    - 构件可以是类、库、框架、服务等。
    - 构件的设计应具有**高内聚、低耦合**的特点。
    - **接口类** 是只有方法没有组件的类，没有内部结构，也没有关联。
    - **全局变量初始化类** 是只有属性没有方法的类，只定义常量。
- **优点**：
    - **提高开发效率**：通过重用现有构件，减少了从头开始编写代码的工作量。
    - **降低开发成本**：重用构件可以节省开发时间和资源。
    - **提高软件质量**：使用经过测试的构件，可以提高软件的可靠性和稳定性。
    - **易于维护**：构件化设计使得软件更易于维护和升级。
    - **促进标准化**: 通过标准化构件，可以降低成本。
- **缺点**：
    - **构件管理**：需要有效地管理和维护可复用的构件库.
    - **构件集成**：集成不同的构件可能存在兼容性问题，需要仔细设计接口。
    - **构件依赖**：构件之间可能存在依赖关系，需要仔细管理。
- **适用场景**：
    - 需要快速开发和交付的应用程序。
    - 具有大量可重用功能的应用程序。
    - 需要高度模块化和可维护性的应用程序。
- **与面向对象设计的关系**: 基于构件的开发与面向对象设计密切相关。**类可以被视为构件的基本组成部分**，并且可以通过定义良好的接口进行交互。**在面向对象设计中，强调类的高内聚和低耦合，这也适用于构件的设计**。

### **4.4.2. 形式化方法模型 (Formal Methods Model)**

- **概念**：形式化方法模型是一种**基于数学和逻辑**的软件开发方法。它使用形式化的语言和工具来**描述、验证和验证软件的正确性**。
- **核心思想**：通过**严格的数学推理**来确保软件的规范、设计和实现符合预期。
- **方法**：
    - **形式化规约**：使用形式化的语言（例如，Z 语言、B 方法等）来描述软件的需求和功能。
    - **形式化验证**：使用数学证明或模型检测等技术来验证软件设计的正确性。
    - **形式化推导**：使用形式化的方法将抽象的规约转换为可执行的代码。
- **优点**：
    - **提高软件可靠性**：通过严格的验证，可以最大限度地减少软件中的错误。
    - **提高软件安全性**：形式化方法可以帮助检测和防止安全漏洞。
    - **减少测试工作量**：通过形式化验证，可以减少软件的测试工作量。
- **缺点**：
    - **复杂性高**：形式化方法需要专业的数学和逻辑知识。
    - **成本高**：使用形式化方法进行开发需要大量的时间和资源。
    - **难以理解**：形式化的规约和验证过程可能难以被非专业人士理解。
- **适用场景**：
    - 安全性和可靠性要求极高的软件系统，例如航空航天、核电站、医疗设备等。
    - 对正确性有严格要求的软件系统。
    - 大型复杂系统中的关键组件。

### **4.2.3. 面向方法的软件开发 (Method-Oriented Software Development)**

- **概念**：面向方法的软件开发是一种**强调使用特定方法或技术**进行软件开发的软件开发方法。
- **核心思想**：
    - **过程化**: 软件开发被视为一系列有序的活动，例如需求分析、设计、编码、测试和部署。
    - **结构化**: 每个活动都有明确的目标、输入和输出，并且遵循一定的规则和规范。
    - **方法指导**: 使用特定的方法来执行每个活动，例如，**用例建模，数据库设计，架构设计** 等。
- **方法示例**：
    - **用例建模 (Use Case Modeling)**：使用用例来描述用户如何与系统交互。
    - **数据建模 (Data Modeling)**：使用类图来描述系统中的数据结构和关系。
    - **行为建模 (Behavior Modeling)**：使用状态图和时序图来描述系统的行为。
        - **状态图**: 用于描述类的状态以及状态之间的转换。
        - **时序图**: 用于描述对象之间的交互以及消息传递的顺序。
    - **架构设计 (Architectural Design)**：使用架构风格和模式来描述系统的整体结构。
    - **详细设计 (Component-Level Design)**：使用活动图或伪代码来描述组件的内部实现。
- **优点**：
    - **提高开发效率**：使用明确的方法和工具，可以提高开发效率。
    - **提高软件质量**：遵循规范化的方法可以减少错误并提高软件的可靠性。
    - **易于管理**：通过分解任务和定义清晰的责任，易于管理项目。
    - **促进沟通**：使用统一的方法和符号，促进团队成员之间的沟通和协作。
- **缺点**：
    - **灵活性差**：过分强调方法和规范，可能导致灵活性较差，难以适应变化。
    - **学习成本高**：团队成员需要学习和掌握特定的方法和工具。
- **适用场景**：
    - 具有明确需求和目标的软件项目。
    - 需要规范化和标准化的软件开发项目。
    - 需要团队成员密切协作的项目。

**总结**

- **基于构件的开发**强调重用现有构件来提高开发效率和质量。
- **形式化方法模型** 强调使用数学和逻辑方法来验证软件的正确性。
- **面向方法的软件开发** 强调使用特定的方法和技术来指导软件开发过程。
- 这三种方法都旨在提高软件的开发效率、质量和可靠性，并且可以根据不同的项目需求进行选择和组合使用。
## **4.3统一过程（Unified Process）**。

**统一过程（Unified Process）**是一种**迭代和增量式**的软件开发过程框架。它不是一个具体的、单一的开发方法，而是一个可定制的过程框架，可以根据不同的项目需求进行调整。统一过程的目标是**提高软件开发的质量、效率和可预测性**。

### 4.3.1**核心概念和特点**

- **迭代和增量**：
    - 统一过程将软件开发分为**多个迭代周期**，每个迭代周期都包含**需求分析、设计、实现、测试和部署**等活动。
    - 每个迭代周期都会产生一个**可工作的软件增量**，该增量可以逐步交付给客户。
    - 迭代允许在开发过程中**不断地学习和调整**，从而更好地适应变化。
- **用例驱动**：
    - **用例（Use Cases）**是统一过程的核心驱动因素。用例描述了用户如何与系统交互，并定义了系统的功能需求。
    - 用例用于**指导需求分析、设计、实现和测试**等活动。
- **以架构为中心**：
    - 统一过程强调在早期阶段建立一个**健壮的软件架构**。
    - 架构是**软件系统的蓝图**，定义了系统的整体结构和组件之间的关系。
    - 架构可以帮助**减少风险，提高软件的可维护性和可扩展性**。
- **风险驱动**：
    - 统一过程强调在开发过程中**识别和管理风险**。
    - 风险管理包括**风险识别、评估、缓解和跟踪**等活动。
    - 通过管理风险，可以**提高项目的成功率**。

### 4.3.2**统一过程的阶段**

统一过程通常分为四个阶段，每个阶段都包含若干个迭代周期：

1. **初始阶段（Inception Phase）**：
    - **目标**：定义项目的**范围、愿景和初步需求**。(相当于沟通（C)和策划（P）活动）
    - **主要活动**：
        - **业务建模**，理解业务需求。
        - **需求收集**，建立初始的需求文档。
        - **风险评估**，识别关键的风险。
        - **制定项目计划**，包括时间表、预算和资源分配。
        - **确定项目的可行性**。
    - **产出**：**项目愿景文档、初步用例模型、初始风险列表和项目计划**。
2. **细化阶段（Elaboration Phase）**：
    - **目标**：**详细描述需求，建立软件架构**。（包括沟通（C）和建模(M)）
    - **主要活动**：
        - **详细的需求分析**，定义详细的用例。
        - **建立架构原型**，验证架构设计。
        - **详细的风险评估**，制定风险缓解计划。
        - **建立详细的开发计划**，包括迭代计划和里程碑。
    - **产出**：**详细的用例模型、软件架构文档、风险缓解计划和详细的迭代计划**。
3. **构建阶段（Construction Phase）**：
    - **目标**：**开发和测试软件的增量**。（与通用软件过程的构建活动相同）
    - **主要活动**：
        - **编码**，实现用例。
        - **单元测试**，确保代码质量。
        - **集成测试**，测试组件之间的交互。
    - **产出**：**可工作的软件增量，包括经过测试的代码和文档**。
4. **交付阶段（Transition Phase）**：
    - **目标**：将**软件交付给用户并提供支持**。（包括通用构建活动的后期和通用部署的第一部分）
    - **主要活动**：
        - **软件部署**，将软件安装到目标环境。
        - **用户培训**，提供用户文档和培训。
        - **支持和维护**，解决用户问题和缺陷。
    - **产出**：**部署的软件，用户文档和培训材料**。

**统一过程的优点**

- **灵活性**：统一过程是一个灵活的过程框架，可以根据不同的项目需求进行调整。
- **可预测性**：通过迭代和风险管理，可以提高项目的可预测性。
- **高质量**：通过用例驱动、以架构为中心和风险驱动，可以提高软件的质量。
- **易于管理**：通过阶段和迭代，可以更好地管理项目。
- **用户参与**：用户可以在每个迭代周期中提供反馈，从而确保软件满足用户需求。

**统一过程的缺点**

- **复杂性**：统一过程是一个复杂的过程框架，需要专业的知识和技能。
- **文档要求高**：统一过程强调文档，可能需要大量的时间和资源。
- **可能过于重量级**：对于小型项目，统一过程可能过于重量级，效率不高。

**与其他过程模型的比较**

- **瀑布模型**：统一过程与瀑布模型不同，**瀑布模型是线性的，而统一过程是迭代的**。统一过程可以更好地适应变化，而瀑布模型难以适应需求的变化。
- **敏捷开发**：统一过程与敏捷开发都强调迭代和用户参与，但统一过程更强调架构和风险管理。**敏捷开发更加轻量级，而统一过程更加结构化**。

**总结**

统一过程是一种**迭代和增量式**的软件开发过程框架，它强调**用例驱动、以架构为中心和风险驱动**。统一过程适用于**各种规模和类型的项目**，并且可以根据不同的项目需求进行调整。通过使用统一过程，可以提高软件开发的**质量、效率和可预测性**。
